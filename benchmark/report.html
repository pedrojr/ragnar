Ragnar ranks the right file much higher than grep, but a real agent did not spend less

In search, Ragnar wins clearly: MRR 0.67 against 0.36 for grep, with a gain in all four languages, largest in Java. With a real agent, answers were just as correct (98% with Ragnar and 98% without it), in 22% fewer turns. There were no savings: context showed no proven change and cost was 17% higher. On these small to medium projects, an agent with grep already solves almost everything.

Comparison on 8 open source projects, in Delphi, Java, C# and Go. The main numbers come from questions kept out of all tuning.

What changed in the project

Core files reach the index

Problem: max_file_kb = 300 silently kept HeidiSQL's main.pas and dbconnection.pas and commons-lang's StringUtils.java out of the index: the very files that change most.

Fix: A 2 MB default limit, and every run reports what it left out and why.

Evidence: HeidiSQL went from 1,573 to 2,065 chunks, and 5 core files came back to the index.

Delphi the grammar cannot read

Problem: 44 of 189 units gave parse errors. dbconnection.pas lost 43% of its routines, and chunks cut methods in half.

Fix: When the grammar fails, a scan of routines and types sets chunk boundaries and symbols.

Evidence: HeidiSQL went from 6,196 to 9,082 symbols.

Folders that looked like build output

Problem: Folders named target, build or Win32 were skipped even with real sources: a Java package org/acme/target, or Lazarus sources in win32/.

Fix: These folders only count as build output outside the source root, and Win32 only together with Debug or Release.

Evidence: Covered by unit tests with the real paths.

Lexical ranking by rarity

Problem: Words such as how, the and is weighed as much as circuit. Without stemming, escaped did not find EscapeString.

Fix: BM25-style weight by rarity, English and Portuguese stopwords, light stemming, and extra weight for path and symbol.

Evidence: Lexical only, on dev: MRR 0.65, against 0.42 for grep.

Whole-file list

Problem: A chunk rarely holds every word of a question. On huge units, grep won by looking at the whole file.

Fix: Files holding the most query weight join the fusion through their best chunk.

Evidence: The largest single contribution on dev: MRR from 0.59 to 0.65.

References instead of dropped hits

Problem: The token budget threw good results away.

Fix: What does not fit comes back as path, lines and symbol.

Evidence: Recall@10 from 0.76 to 0.83 on dev, for about 220 tokens.

New MCP tools

Problem: No answer to who calls X, no map of huge files, and no way to read code outside this disk.

Fix: find_references, file_outline and read_code. find_symbol takes TOrder.Cancel and matches part of a name.

Evidence: On dev, caller questions dropped to about 420 tokens.

The agent started using the index

Problem: With the original AGENTS.md note, the real agent never called Ragnar: 0 of 2 measured runs used the index, with the server up.

Fix: The project note, the server instructions and the search_code description now say when to start with the index.

Evidence: 33 of 34 dev runs called Ragnar after the change.

Smaller default budget

Problem: At 4,000 tokens per search, the real agent spent 37% more context than with grep.

Fix: A default of 5 hits within 2,000 tokens.

Evidence: On dev, median context from 34.2k to 27.8k, against 25.1k for grep.

Reindexing without paying for embeddings again

Problem: Any settings or chunker change reprocessed every vector. On a CPU, that costs hours.

Fix: Vectors reused by content hash, and texts sent to the embedder by length.

Evidence: Reindexing jsoup took 84 s, against 543 s from zero.

Secrets in fixtures

Problem: One gitleaks finding stopped the whole repository.

Fix: index.secret_action = "skip" leaves only those files out. The default stays fail.

Evidence: 3 of the 8 repositories would have stopped.

Chunks and errors

Problem: Chunks of up to 96,000 characters, 293 of 608 Serilog chunks with no symbol, and a 4xx from the embedder with no clear message.

Fix: Huge nodes split, whole-file chunks name their declarations and namespace, and errors are clear.

Evidence: Serilog went from 293 to 8 chunks with no symbol, and HeidiSQL's largest chunk from 17,330 to 2,778 characters.

Limits of this result

  • The token difference of the scripted arms, 56k against 2.2k, does not hold for a real agent. Agents use grep with partial reads, which costs far less than that model assumes. For cost, trust the real agent section.
  • The agent gets almost everything right in both modes on these repositories, which have between 100 and 500 indexed files. They do not show where an index should help most: large codebases, and several codebases at once.
  • On cross-file flow and Portuguese questions, the right file usually comes back, but the snippet with the evidence does not always fit in 2,000 tokens. On flow, the evidence reached the context in 1 of 8 questions, against 5 of 8 for grep. The agent still has to read the file.
  • The agent's correct-answer rule is simple: cite an expected file. It does not judge the quality of the explanation.
  • Curated questions were written by reading the code, which favors vocabulary close to the project's. History questions balance part of this, but they favor files that change often.
  • Caller answers use find_references when the question carries the identifier. On a natural language question, the agent has to discover that name first.
  • Ragnar cannot say something does not exist: it returns the closest match.
  • The comparison with v0 covers only 5 repositories, because indexing on a CPU took hours.
  • Serilog fell from 0.52 to 0.44 on holdout, on 33 questions, but rose from 0.46 to 0.55 on the 48 dev questions. At these sample sizes the fall looks like variation, not a regression, but that is not proven.
  • Reranker, multi-query, HyDE and contextual retrieval were not tested: they need models that did not run here.
  • v0 had aggregate results visible during the work, but no tuning used holdout results.

Next steps

  • Repeat on a large monorepo, with thousands of files, where grep and reads cost more.
  • Measure sessions that edit code, not only questions.
  • Test a light local reranker, because the remaining gain is in the order of the first results.
  • Link .dfm, handler and SQL: Delphi forms still depend on text search.

Method

Each question ran in both arms on the same snapshot, pinned by commit. Without Ragnar: one git grep per term, files ranked by distinct terms, then the top five read in turn until the answer showed up. This is the best case for grep, because a real agent cannot always tell it has found the answer. With Ragnar: one search_code call, or the specific tool for symbol and caller questions.

Curated questions have their file and evidence checked against the snapshot. History questions come from the subjects of commits after the snapshot. The split between dev and holdout is a hash of the question id. The final run started from an empty database, with no reused vectors.

Final run: 12,629 chunks in 1.0 CPU hours, database of 204 MB. Median latency of 125 ms per search, against 512 ms for grep with reads, on a single database with the machine shared with other work: this is not a production figure.

gitleaks flagged files in 3 of the 8 repositories (dmvc, caddy, gin). With the default fail, those repositories would not index. The benchmark runs without the scan, and index.secret_action = "skip" now covers this case in production.
